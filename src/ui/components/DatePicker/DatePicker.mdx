# DatePicker

DatePicker renders a date input plus a calendar popover the user opens to pick visually. The single mode collects one date; the range mode collects a `{ start, end }` pair. Reach for it whenever the user picks a specific calendar date — appointments, deadlines, filters, event boundaries — and benefits from seeing the surrounding month.

## When to use

- Use DatePicker for any field that accepts a calendar date — appointments, deadlines, filter boundaries, birthday entry, schedule pickers.
- Use `mode="single"` (default) for one date; `mode="range"` for two-bounded selections (filter ranges, event durations, vacation request periods).
- Use `minDate`, `maxDate`, and `disabledDates` to constrain the selectable set — server-side availability windows, lead-time requirements, blackout dates.
- Use `format` (consumer-provided format string) when the visible value should match a locale or domain convention; the underlying value stays a `Date` object.
- Use the compound shape (`DatePicker.Input` + `DatePicker.Calendar`) when the consumer needs to position the calendar separately from the input — inline embeds, custom layouts.

## When not to use

- Use `Input type="date"` for surfaces that benefit from the platform-native picker — mobile, simple internal tools, surfaces where the native UX wins.
- Use `TimePicker` for time-of-day fields; pair the two when the field needs both date and time.
- Use a custom calendar component for surfaces that need multi-month views, week / day pickers, or domain-specific behaviors (rotating shifts, fiscal calendars).

## Anatomy

DatePicker is composed from a compound API. The root `DatePicker` mounts a context provider carrying the current value, mode, and the open state. `DatePicker.Input` renders the field showing the formatted current value with a leading calendar glyph; clicking the input (or the trailing calendar button when `showCalendarButton`) opens the popover. `DatePicker.Calendar` is the portaled popover containing the `month header` (with previous / next navigation and the current month + year), the `weekday row` showing day-of-week labels, and the `day grid` with each cell as a `<button>` for selectable dates (disabled cells render but skip focus); in `mode="range"`, the selected range fills with a tinted background between start and end.

## Accessibility

DatePicker follows a WAI-ARIA-aligned Date Picker pattern. The input is a native `<input>` accepting typed values directly (the user does not have to open the calendar to enter a date); the calendar popover carries `role="dialog"` with `aria-label="Date picker"` so assistive tech identifies the surface when it opens.

Keyboard navigation inside the calendar: arrow keys move the focus by one day (left/right) or one week (up/down); Page Up / Page Down jump by month; Shift + Page Up / Page Down jump by year; Home and End move to the start / end of the visible week; Enter selects the focused day and closes the popover; ESC closes without selecting. Tab moves between the navigation chrome (month / year buttons) and the day grid.

Each day cell carries `aria-label` with the full date string ("Tuesday, March 14, 2024") so assistive tech announces the day in context rather than just the number. Selected cells have `aria-selected="true"`; disabled cells have `aria-disabled="true"` and are skipped during arrow navigation. In `range` mode, both the start and end cells carry `aria-selected="true"` and intermediate cells are announced as "in selected range".

For accessible field labeling, wire a visible `Label` to the input via `htmlFor`. When the picker opens, assistive tech announces the dialog and the currently focused date together — the user does not lose context about which field they were filling.

The visible value format is purely visual; the underlying `value` is always a `Date` object (or a `{ start, end }` shape in range mode). The consumer combines this with timezone awareness if the domain requires it.
