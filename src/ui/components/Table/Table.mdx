# Table

Table renders tabular data with optional sorting, pagination, filters, row selection, per-row actions, and an empty state. Reach for it for any list view where the rows have a regular structure and the user benefits from columns the eye can scan, or use `DataGrid` when the surface needs the richer feature set on top of Table.

## When to use

- Use Table for any tabular list of items with regular columns — invoices, users, issues, products, audit log rows.
- Use `pagination` for surfaces with more rows than fit on a single screen; pass the page state from the parent so the consumer drives navigation.
- Use `filters` to render filter controls above the table that the user composes; the filter values reach the parent via `onFilter` to drive the data set.
- Use `selectable` + `selectedRows` + `onSelectionChange` for bulk-action surfaces; the header checkbox toggles the visible page selection and announces "indeterminate" when partial.
- Use per-row `actions` to expose row-level affordances (Edit / Delete / Duplicate) inline; the actions render as a `Dropdown` or button group depending on the consumer's configuration.

## When not to use

- Use `DataGrid` for surfaces that need column resize / reorder, grouping, export menus, virtual scrolling, or multi-column sort. DataGrid extends Table with that machinery.
- Use `DataTablePattern` when the surface fits the pre-built "search + table + pagination" shell exactly — that pattern wraps Table.
- Use a plain `<ul>` or card grid when the data is not tabular — Table's grid mechanics add cost without value for non-table data.

## Anatomy

Table stacks vertically: an optional `filters region` at the top (rendered when `filters` is configured); the `table` element itself with a `<thead>` containing the `column header row` (each cell sortable when the column is sortable, with the visible sort indicator) and a `<tbody>` containing the `data rows` (each `<tr>` with the configured cells, optional leading selection checkbox, and trailing actions); the `pagination region` below the table when `pagination` is configured; the `empty state region` replaces the body when there is no data, using the consumer's `emptyStateTitle` / `emptyStateMessage` / `emptyStateIllustration` / `emptyStateAction`.

## Accessibility

Table renders native `<table>`, `<thead>`, `<tbody>`, `<th>`, `<tr>`, `<td>` so assistive tech navigates using the platform's table mode (Ctrl + arrows on macOS VoiceOver; similar on JAWS / NVDA). The semantic markup is what makes the grid navigable without extra wiring.

Sortable column headers carry `aria-sort="ascending" | "descending" | "none"` reflecting the current sort; activating the header (Enter / Space on a focused `<th>` containing a button) toggles sort and announces the new state.

Selection checkboxes are native `<input type="checkbox">` with explicit `aria-label="Select row <id>"` and `aria-label="Select all rows on this page"` on the header checkbox. The header checkbox shows the indeterminate state when some rows are selected; assistive tech announces "mixed" instead of "checked" / "unchecked".

The filters region is wrapped in `<form role="search">` (or a plain region with `aria-label="Filters"`) so assistive tech identifies it as a control cluster. Applying a filter announces the new row count via `aria-live="polite"` on the table body region.

For the empty state, the region carries `role="status"` so the absence is announced when the table resolves to zero rows.

The `actions` per row render as a `Dropdown` trigger when there are more than two actions, exposing the `Dropdown`'s WAI-ARIA Menu semantics — the consumer does not wire menu roles directly.

## Architecture

Table's state — pagination, sorting, filters, selection — is owned by an internal `TableProvider` mounted by the root `Table` component. The provider exposes state through a `TableContext` consumed by the subcomponents (header cells reading the sort state, body rows reading selection, pagination controls reading page state). Most consumers do not interact with `TableProvider` directly; the simplified Table props cover the common case.

Two modes drive the data path:

- **Client-side mode** (default): the provider applies filtering, sorting, and pagination to the `data` array on every state change. Suitable for small to medium datasets where the entire list fits in memory.
- **Server-side mode**: the consumer passes `pagination.total` from outside and wires `pagination.onPageChange`, `sortColumn` / `sortDirection` + `onSort`, and `filters.onFilter` to fetch fresh data from an API. The provider manages UI state only; data processing happens externally.

Each state domain supports controlled and uncontrolled modes — pass the state prop + handler for controlled, omit them for uncontrolled internal state.

When the consumer needs to read state from outside Table (a status bar showing "3 selected" outside the table chrome), wrap the surface in `TableProvider` directly with the same configuration and consume `useTableContext()` — the alternative composition path that powers the simplified Table inside.
