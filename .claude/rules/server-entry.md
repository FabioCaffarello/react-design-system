# Server entry rules

Issue #150 added a second entry point `@fabio.caffarello/react-design-system/server` that ships only the components whose render tree is safe to run inside a React Server Component. This file is the canonical contract for what may live in that entry, how to add to it, and what catches regressions.

## The shape

The dist carries four independent Vite builds (`dist/hooks/` — the public-hooks client entry from `vite.config.hooks.ts`, issue #203, see `.claude/rules/hooks.md` — and `dist/granular/` — the preserveModules client tree from `vite.config.granular.ts`, issue #208, decision record in that config's header — are out of this rule's scope). The two that define the server contract:

- `dist/index.{js,cjs}` — the **main entry** (`.`). Starts with `"use client";` (banner injected by `vite.config.ts`). Carries everything: providers, hooks, primitives, components, layouts, tokens. This is the unchanged default; consumers who import nothing from `./server` see identical behaviour to RDS 2.x.
- `dist/server/index.{js,cjs}` — the **server entry** (`./server`). Has **no** `"use client"` banner. Re-exports a curated subset audited as server-safe. Externalises every third-party dep (`react`, `react-dom`, `react/jsx-runtime`, `lucide-react`, `class-variance-authority`, `clsx`, `tailwind-merge`, `react-hook-form`) so directives those packages ship with reach the consumer's bundler intact.

The two bundles share no chunks. The cva cross-chunk regression that defeated the original multi-entry layout (see `vite.config.ts` header) cannot fire across separate Rollup graphs.

## What counts as "server-safe"

Server-safety is decided on **two axes**, by two different gates:

**Axis 1 — static, source-walk classification.** A module passes when it AND every value-imported source inside `src/ui/` is free of the React client APIs `useState`, `useEffect`, `useLayoutEffect`, `useReducer`, `useContext`, `useRef`, `useImperativeHandle`, `useCallback`, `useMemo`, `useId`, `useTransition`, `useDeferredValue`, `useSyncExternalStore`, `useInsertionEffect`, `useOptimistic`, and `createContext`. This is what `scripts/lib/server-safe.mjs` checks, and what gates the source-level validator at pre-push and CI lint.

**Axis 2 — runtime RSC smoke.** The Next 16 fixture at `fixtures/next-smoke/app/page.tsx` imports the **entire** server-safe surface in one Server Component and runs `next build`. Any component that emits a function-typed prop on a DOM element UNCONDITIONALLY (a local closure assigned every render, regardless of consumer input) fails with `Event handlers cannot be passed to Client Component props`. The static analyser cannot see this — distinguishing "always-on local closure" from "consumer pass-through" requires AST origin tracking with a real risk of false positives on legitimate components (e.g. `onClick={onClick}` where the prop is `undefined` when not passed is fine; `onClick={handleClick}` where `handleClick` is a local `const` is NOT). The runtime is the authoritative judge; the smoke runs it.

A module is server-safe only when it passes **both** axes.

The current set is **36 exports**, listed in `src/ui/server.ts` and re-derived on demand by `node scripts/analyze-server-safe.mjs`. The inventory counts **value exports**, not "top-level components" — subcomponents of compounds (`Card.Header`, `DialogHeader`, etc.) count individually because they are re-exported individually from `src/ui/server.ts` and the consumer imports them by their named export. A compound parent like `Card` and its 5 dot-notation children (`Card.Header`, `Card.Title`, `Card.Subtitle`, `Card.Actions`, `Card.Body`) contribute 6 lines to this count, not 1. The parent annotation in parentheses below makes the compound relation visible:

- **Primitives (11)**: `Badge`, `Button`, `Chip`, `ErrorMessage`, `Info`, `Label`, `Progress`, `Separator`, `Skeleton`, `Spinner`, `Text`.
- **Layouts (2)**: `Container`, `Stack`.
- **Components (23)**: `Breadcrumb`, `Card`, `CardHeader (Card.Header)`, `CardTitle (Card.Title)`, `CardSubtitle (Card.Subtitle)`, `CardActions (Card.Actions)`, `CardBody (Card.Body)`, `DialogHeader (Dialog.Header)`, `DialogFooter (Dialog.Footer)`, `DrawerHeader (Drawer.Header)`, `DrawerFooter (Drawer.Footer)`, `FilterChips`, `HeaderActions`, `HeaderNavigation`, `HeroSection`, `MenuSeparator (Menu.Separator)`, `NavbarSeparator`, `PageHeader`, `Stat`, `StatGroup`, `TableCell (Table.Cell)`, `TabsAsLinks`, `Timeline`.

Badge, Label, Separator, and Card were promoted in issue #155: each previously held `useMemo` (and Card additionally `useCallback`) calls that were purely decorative — they memoized class-string concatenations and a single `onClick !== undefined` boolean, not render-driving state. Inlining those expressions removed the only barrier without changing observable behaviour or perf (string concatenation is nanoseconds; `React.memo` on the component is preserved and continues to gate re-renders at the consumer-prop boundary).

**`Button` promoted in issue #224 — same #155 mechanism.** Its body held six purely-decorative `useMemo` calls (the class string, the `isIconOnly` boolean, the fallback aria-label, the spinner variant/size, the loading-icon node), none gating render-driving state. Inlining them removed the only axis-1 barrier; `React.memo` on the component is preserved. Axis 2 is satisfied because Button never assigns a handler to its DOM element unconditionally — `onClick`/`onKeyDown`/etc. arrive through `...props` and are `undefined` until the consumer passes them, so the server forms the consumer needs (`<Button>`, `<Button asChild><Link/></Button>`, `<Button type="submit">`) emit no function prop and pass the Next 16 smoke. This unblocks the brasil-a-vera consolidation's most-used primitive (27 consumers, 13 of them Server Components) without forcing the `"use client"` boundary onto those routes. Issue #224's other half — `Input` — stays main-entry-only for now: it has **genuine** client state (`useState` password toggle, `useId`, `useCallback` clear/toggle handlers), so it is not a de-memoization away from server-safe; promoting it needs a base/affix split tracked as a separate change.

**`PageHeader` promoted in issue #178.** Its body never used a React client API — the `"use client"` directive at the top of `PageHeader.tsx` was vestigial. The analyser nonetheless classified it client-only because of a barrel import `import { Text } from "../../primitives"` that the static walk follows transitively into `primitives/index.ts`, which re-exports `Input.tsx` (`useMemo`). Replacing the barrel with a concrete-source-file import (`import Text from "../../primitives/Text/Text"`) and removing the directive flipped the classification with no behavioural change. This is the exact mechanism rule 1 below exists to prevent on `src/ui/server.ts`; the same anti-pattern in non-entry files is not gated, but `#178` is the canonical worked example of it as a latent blocker on promotion.

**`Stat` + `StatGroup` shipped in issue #166 (consolidated with #164).** The original #166 (`KpiStrip`) and #164 (`StatsGrid`) proposed two near-identical components for the same visual archetype — a row/grid of metrics with 1-px dividers between cells. The verdict consolidated them into a single compound: `<StatGroup>` is the container (`layout: 'strip' | 'grid'`, `cols: 2 | 3 | 4`); `<Stat>` is the atom (`value`, `label`, `hint?`, `icon?`, `align: 'start' | 'center'`, `tone: 'neutral' | 'success' | 'warning' | 'error'`). Both ship in `./server` (pure presentation). #164 closed as a duplicate of #166. The divider technique is a single piece of CSS — the container carries `bg-line-default` with `gap-px`, each `Stat` masks its own area with `bg-surface-base`, so the 1-px of gap exposes the line color as the divider. This works identically for strip (vertical dividers only) and grid (vertical AND horizontal dividers as the grid reflows). The empty-state contract (the em-dash placeholder with `aria-label="No data"` when `value` is `null` or `undefined`, while `0`/`""`/`false` remain legitimate values) is documented in the `Stat` JSDoc and exercised by the test + a dedicated story; the `tone` prop tints ONLY the `hint` line, a contract that is also documented in the JSDoc to keep future expansions explicit (an icon or value picking up `tone` would be a semver-bound change, not an implicit growth of the prop).

**`Card` compound shipped in issue #165.** The flat `Card` gained five presentational subcomponents — `Card.Header`, `Card.Title`, `Card.Subtitle`, `Card.Actions`, `Card.Body` — exposed via dot-notation on the root and also as named exports. Each lives in its own source file so the server/client boundary is per-file: every subcomponent is server-safe (no hooks, no handler-as-DOM-prop) and ships in `./server`. The consumer composes interactive children (e.g. `<Button onClick>`) inside `<Card.Actions>`; the wrapper stays server, the Buttons cross the RSC boundary as client references — same mechanism that already lets `DialogFooter` host client Buttons. The root `Card` also accepts a new opt-in prop `asSection={true}`: when set, the root renders `<section>` (a landmark) instead of `<div>`. To prevent the silent-anonymous-landmark trap (`<section>` without a name announces "region" with no identifier, hurting AT navigation), the root emits a dev-only `console.warn` when `asSection={true}` is paired with neither `aria-labelledby` nor `aria-label`. The warn is guarded by `process.env.NODE_ENV !== "production"` so the consumer's bundler dead-code-eliminates it from prod bundles; the pattern mirrors the `asChild` precedent in `Button.tsx`. `asSection` defaults to `false` to keep the existing flat usage byte-for-byte identical.

**`FilterChips` shipped in issue #162.** The chip-group filter-bar shell the consumer (brasil-a-vera) replicated on every listing page: a `role="group"` container with an optional `label` rendered as neutral text (deliberately NOT `<fieldset>`/`<legend>` — chips are navigation/selection affordances, not form controls) and a flex run of `Chip`s that wraps by default (`wrap?: boolean`, default `true` → `flex-wrap`; `false` → `flex-nowrap`). When `label` is a plain string it doubles as the group's `aria-label`; an explicit consumer `aria-label` overrides it (spread after the derived value); a non-string `ReactNode` label derives nothing. Pure presentation — zero hooks, zero handlers on the DOM — so it ships in `./server`; the interactive identity lives in each `Chip` (`onClick`/`onRemove`, or the zero-JS `<Chip asChild><Link/></Chip>` form from #154), which crosses the RSC boundary as a client reference when needed.

**`HeroSection` shipped in issue #163.** The top-of-page hero the consumer (brasil-a-vera) replicated across landing/listing routes: a named `<section>` landmark with six slots — `kicker` / `title` (required) / `description` / `actions` / `kpis` / `meta` — in three visual treatments (`plain` / `gradient` / `gradient-glow`) and two alignments (`start` / `center`). Distinct from `PageHeader` (contextual navigation: breadcrumb + title + actions); the hero is a page **introduction** with visual identity and a KPI slot. Pure presentation — zero hooks, zero handlers on the DOM — so it ships in `./server`; interactive children land in the opaque `actions` / `kpis` slots (e.g. `<Button onClick>`, `<StatGroup>`) and cross the RSC boundary as client references. Two patterns are reused verbatim from earlier server-safe work: the accessible name derives from a string `title` (the `FilterChips` `label` mechanism — explicit `aria-label`/`aria-labelledby` overrides it, and a non-string `title` with no name triggers the dev-only `console.warn` guarded by `typeof process !== "undefined" && process.env.NODE_ENV !== "production"`, the `Card` `asSection` precedent), and `Text` is imported from its concrete source file (`../../primitives/Text/Text`, never the barrel) so the analyser walk stays clean — the #178 anti-pattern. The three variants are backed by `.hero-gradient` / `.hero-glow` utility classes in `src/styles/utilities/gradients.css` that compose existing semantic surface tokens (`--color-surface-brand-subtle` → `--color-surface-secondary-subtle`) and the `--glow-primary` token, so they flip with the active theme and carry no raw color value into the component.

**`TabsAsLinks` shipped in issue #210.** The URL-navigation tab bar the consumer (brasil-a-vera) hand-rolled as a ~30-line `TabBar` plus two duplicated `SubTabs`. It is the **server-safe counterpart to the interactive `Tabs` widget** (which is `"use client"`, provider/context-driven): each tab is a real `<a>` to a distinct URL, and the active state is a caller-supplied boolean (`items: { label, href, active?, icon?, count? }[]`) derived from `pathname`/`searchParams` — the component does no detection of its own, so it needs no hooks. Because the tabs navigate rather than toggle in-page panels, it uses the **navigation pattern** — a named `<nav>` landmark with `aria-current="page"` on the active link — NOT `role="tab"`/`tablist` (which would promise arrow-key semantics links don't have); this mirrors the existing client `Navigation` component's a11y shape while staying RSC-renderable. An anonymous `<nav>` triggers the dev-only warn (Card `asSection` precedent). Two visual tiers via `variant: 'default' | 'sub'` (primary tab bar vs nested sub-tabs), underline style matching `NavLink`'s `underline` variant. Pure presentation — zero hooks, zero DOM handlers — so it ships in `./server`; it defaults to a plain `<a>` (zero JS) and accepts `linkComponent?: ElementType` (e.g. `next/link`) so the consumer keeps client-side navigation, with the router link crossing the RSC boundary as a client reference. It deliberately does NOT use `NavLink` internally (that primitive is `"use client"` — `useMemo`/`useCallback`) so the server classification stays clean.

**`AutocompleteOption` removed in #160.** Originally promoted in #150, it passed axis 1 (no hooks, no `createContext`) but failed axis 2 once the smoke fixture was extended to render the full surface: its source emits `<div onClick={handleClick}>` where `handleClick` is a local closure that calls the required `onSelect` prop. There is no guard pattern available — `onSelect` is required, so `handleClick` must always exist; the only honest fix is to keep the component on the main entry (where its source `"use client"` directive applies) and remove it from this entry. The same #160 sweep also fixed `Card`'s analogous bug (`onKeyDown={handleKeyDown}` → `onKeyDown={isInteractive ? handleKeyDown : undefined}`) — Card kept its place because its `onClick` is optional and the handler can be elided when `isInteractive` is false.

Type-only imports (`import type { … }` and `import { type X, … }` inline specifiers) are erased by TypeScript before the bundler runs and are therefore ignored by the analyser. Bare specifiers (anything not starting with `.` or `/`) are not walked because the server build externalises every third-party dep — see the next section for why that matters.

## Hard rules

1. **No barrel imports in `src/ui/server.ts`.** Every re-export must point at a concrete source file (`./primitives/Text/Text`, not `./primitives`). Folder indexes re-export every sibling — `primitives/index.ts` re-exports `Input.tsx`, which is client. A barrel import pulls the whole sibling tree into the server bundle's graph through the analyser walk, and the gate fails immediately. The first inventory analysis on issue #150 was wrong by exactly this mechanism — see the issue body and the `validate-server-entry.mjs` check 2 message.
2. **`src/ui/server.ts` must not start with `"use client"`.** The whole point of the entry is that it doesn't carry the directive. The `validate-use-client-in-dist.mjs` gate asserts the negative on the emitted bundle.
3. **Externalise, don't bundle, third-party deps in `vite.config.server.ts`.** `lucide-react`'s `LucideContext = createContext({})` lives in `node_modules/lucide-react/dist/esm/context.mjs` with a per-file `"use client"` directive — exactly the kind of `createContext` call that crashes the server runtime when it lands in a bundle without a containing directive. Bundling the module strips the directive and the call ends up in `dist/server/index.js`. The fix is to externalise lucide-react (and friends) so the consumer's bundler keeps the directives where they belong. `validate-server-entry.mjs` check 3 catches this regression by reading the React import aliases in the emitted bundle and grepping for their call sites.
4. **Adding a new server-safe component is a six-step commit.**
   - Land the component under `src/ui/{primitives,components,layouts}/`.
   - Run `node scripts/analyze-server-safe.mjs` and confirm the new component appears in the server-safe list (i.e. its transitive value imports are also server-safe). If not, refactor until it is, OR accept that it stays main-entry-only.
   - Add the explicit re-export to `src/ui/server.ts`, importing from the concrete source file (rule 1) and re-exporting the corresponding `*Props` type.
   - **Add a minimal-props render of the new component to `fixtures/next-smoke/app/page.tsx`** (no functions, no class instances). This is the axis-2 gate — the smoke now exercises every server-safe component on every CI run, so an unconditional function-as-DOM-prop emits a `next build` failure with the same shape as #160 before the inventory ever ships. If the component requires a function prop AND emits it unconditionally on a DOM element, do not add it; either refactor the component to guard the handler, or keep the component on the main entry only.
   - Update this rules file's inventory and the export-count gist in `CLAUDE.md` (Server entry section — the count is the only inventory datum CLAUDE.md still carries). Docs-sync per `.claude/rules/docs-sync.md`.
   - Regenerate the a11y baseline: run `npm run test:a11y:baseline` and commit the updated `a11y-baseline.json` in the same PR. The component's stories (5+) join the Storybook set, so the CI `A11y baseline (light/dark)` jobs fail at the `--compare` story-set parity check (`totalStories: CI=N ref=M`) against the committed reference if it is stale — even when every other gate, including the smoke above, is green. Confirm the run reports `critical=0 serious=0` (the floor) before committing. This is local-only (~11min, workers=1) and orthogonal to the server-entry contract, but it is part of the same component-landing commit; see `.claude/rules/components.md` rule 7.
5. **The analyser is the source of truth for axis 1, not the inventory in this file.** If the static lists drift, the analyser wins by default — the inventory here is a human-readable snapshot at the time of writing, the same way `CLAUDE.md`'s Commands section is a snapshot of `package.json` scripts. Rule 4 step 5 exists to keep the snapshot fresh; CI's `validate-server-entry.mjs` gate guarantees the `server.ts` re-export list never silently drifts even if the snapshot does. The smoke fixture is the source of truth for axis 2.

## Why two builds (and not multi-entry)

Three options were on the table for issue #150:

- **A — single Vite build with two entries** (the issue's proposal). Rolled out exactly as described, this recreates the pre-v1.0.0 cva cross-chunk bug: Rollup notices `cva` is imported by both entries and extracts it to a shared chunk that both bundles import via relative path. The shared chunk's path layout breaks once unpacked at the consumer. The proposal's `external: []` doesn't dodge this — `external` is about marking specifiers as runtime-resolved, not about preventing chunk extraction. Rejected.
- **B — `preserveModules: true` plus a per-file directive plugin.** This is what Radix/Mantine do. Reasonable, but the cost is high: a custom Rollup plugin to maintain, a wholesale reshape of `dist/` that consumers see, and a much larger surface for regression on the main entry. The user-facing payoff is ~22 components in a project that ships single-bundle by design. Rejected on cost/benefit.
- **C — two independent `vite build` invocations.** Each is its own Rollup graph. The main build stays single-bundle and unchanged. The server build is its own single-bundle with everything external. They duplicate `cn`/`cva` runtime by ~1.5KB gz, in exchange for **zero** risk of cva cross-chunk leaks. Chosen.

The main build's `external: ["react", "react-dom"]` deliberately stays narrow — that's the historical decision to bundle cva and friends to dodge the v1.0.0 bug. The server build's `external: [react, react-dom, react/jsx-runtime, react/jsx-dev-runtime, lucide-react, class-variance-authority, clsx, tailwind-merge, react-hook-form]` deliberately goes wide — there is no cross-chunk failure mode here, and going wide is exactly what keeps `lucide-react`'s directives intact at the consumer boundary. The two configs make opposite tradeoffs by design.
